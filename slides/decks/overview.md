# Deploying Chap with one binary

## The Climate Health Analytics Platform, its models, OCS and DHIS2, with Docker

What chaps is, what it deploys, and how it works

---

## The problem

To run Chap, you need many parts that work together:

- **chap-core**: the API, a worker, PostgreSQL and Valkey
- **Forecasting models**: each one is a container with its own image
- **Open Climate Service (OCS)**: climate data, with an S3 store
- **DHIS2**: with the Modeling App and the Climate App

Each part has its own compose file, its own ports and its own settings. You
must keep the versions in step, and you must connect the parts.

---

## What chaps is

- **One static binary.** You need Docker and Compose 2.24.4 or newer. You do
  not need Python, uv or a checkout of chap-core.
- **It writes a deployment directory**: compose files, `.env` and `.chaps/`.
- **It runs the deployment** with `docker compose`, and tells you what it did
  and what to do next.
- **Linux and macOS.** On Windows, use WSL with the Linux binary.

```sh
curl -fsSL https://raw.githubusercontent.com/winterop-com/chaps/main/install.sh | sh
chaps doctor
```

---

## The first deployment: three commands

```sh
chaps init mychap --models default
cd mychap
chaps up --wait
```

```text
chap-core   up   http://localhost:8700   2.3.1   auth: off

MODEL                STATE       REACH          LAST PING
chapkit-ewars-model  registered  via chap-core  4s ago

1 model registered
```

`chaps status` says "up" only when chap-core answered as chap-core, not when
compose returned.

---

## What a deployment can hold

| Component | What it is | Turn it on |
| --- | --- | --- |
| `chap-core` | Chap itself: the API, its worker, Valkey and PostgreSQL | on by default |
| models | marketplace models, or your own | `--models ID,ID`, `chaps models enable` |
| `ocs` | Open Climate Service: climate data over STAC and openEO | `--with ocs` |
| `s3` | an S3-compatible object store for OCS | `--with ocs,s3` |
| `dhis2` | a demo or development DHIS2 with its own database | `--with dhis2` |

---

## The shapes of a deployment

`--with` adds components to chap-core. `--only` names the whole set.

```sh
chaps init mychap --with ocs,s3,dhis2        # chap-core and everything
chaps init climate --only ocs,s3             # OCS alone, no chap-core
chaps init dhis --only dhis2                 # a DHIS2 alone
chaps init models --only none --models ID,ID # model services alone
```

- A deployment without chap-core is a normal shape, not a broken one.
- `chaps components enable` and `disable` change the shape later.

## Your files, and the files chaps owns

| File | Who owns it |
| --- | --- |
| `.env` | Written once by `init`. Only pins, the two auth secrets and component settings are added later. The database password is never rewritten. |
| `ocs/climate-service.yaml` | Yours. chaps makes it once, and never rewrites it. |
| `dhis2/dhis.conf` | Yours, on the same terms. DHIS2 does not start without it. |
| every `compose*.yml` | chaps'. They carry the line "Generated by chaps from .chaps/". |

## `chaps sync`

```text
unchanged     compose.yml
unchanged     compose.chaps.yml
unchanged     compose.chapkit-ewars-model.yml
unchanged     compose.marketplace.yml
in sync: 0 written, 4 unchanged, 0 removed
```

- `chaps up` runs `sync` before `docker compose up`.
- The rendering is deterministic: a second sync writes nothing.
- `chaps sync --check` writes nothing and exits non-zero on drift, for CI.
- Sync removes only the overlays that it wrote itself.

---

## chap-core's own compose file, byte for byte

- `compose.yml` is chap-core's `compose.ghcr.yml` at the pinned tag, as
  upstream publishes it. Upstream stays the source of truth.
- chaps makes its changes in `compose.chaps.yml`, a separate `-f` file:
  - the compose project `name:`
  - the API's host port, with `ports: !override`
  - `SERVICEKIT_REGISTRATION_KEY` for the `chap` service
  - the chaps labels on every service
- `!override` is why chaps needs Compose 2.24.4 or newer.

---

## Ports

- **One published port** for chap-core and its models: the API, **8700** by
  default, `--api-port N` otherwise.
- chap-core reaches each model on the compose network at
  `http://<service_id>:8000`. A model needs no host port.
- A model can get a port of its own, from **5001 to 5999**:

```sh
chaps models expose chapkit-ewars-model            # lowest free port, 5001 up
chaps models expose chapkit-ewars-model --bind 127.0.0.1
```

- The components: DHIS2 on **8780**, OCS on **8790**, S3 on none.
- `--port-base` moves the model range. `none` keeps a component off the host.

## Authentication

```sh
chaps init mychap --models default --api-token   # at creation
chaps auth enable                                # later
chaps auth show --reveal                         # read the token
```

- `CHAP_API_TOKEN` protects the whole API, except `/health`, `/health/ready`
  and `/system/info`.
- `SERVICEKIT_REGISTRATION_KEY` is a second secret. The models send it when
  they register.
- chaps writes both to `.env`, and the overlays pass them on.
- Neither change restarts anything: `chaps up` gives the new `.env` to the
  containers.

---

## Pins: everything is pinned

- **Models**: an image tag, a `sha-<commit>` build for marketplace images.
- **chap-core**: a release tag. `init` resolves `latest` to the release it
  points at today, for example `v2.3.1`.
- **DHIS2**: a minor line, `2.42`, so a patch release comes with a pull.
- **OCS and S3**: moving tags (`main`, `latest`), because they publish no
  releases. Set `OCS_IMAGE_TAG` in `.env` to pin one.

Only `chaps models enable` and `chaps update` move a model pin.

---

## up, update, restart: one job each

| Command | What it does |
| --- | --- |
| `chaps up` | Starts what is on disk. Changes no pin. |
| `chaps update` | Moves the pins to what upstream publishes now, and pulls. Touches no container. |
| `chaps restart` | Recreates the services whose image or configuration changed. |

```sh
chaps update --dry-run       # what would move, and nothing changes
chaps update --list-tags     # where chap-core can go
chaps update --chap-tag master
```

---

## The closing line of `chaps update`

Each run ends with one of these lines:

```text
already up to date
updated 1 model pin; restart needed: chap, worker (run `chaps restart`)
updated chap-core v2.3.0 -> v2.3.1; Chap is not running, the new versions start with `chaps up`
updated 1 model pin; nothing needs a restart
pulled a new image for ocs; restart needed: ocs (run `chaps restart`)
```

A move to an older chap-core asks first: an older schema against a migrated
database. `chaps backup create` comes before it.

## `chaps doctor`

One pass over the machine, then the deployment:

- **The machine:** the docker CLI and daemon, the Compose version, the
  architecture, disk, memory for DHIS2, the hosts Chap pulls from, the GitHub
  limit, and the chaps version.
- **The deployment:** the compose project name, the files, sync drift, `.env`,
  the volumes, every host port, the pins, each model image on ghcr, and
  whether Chap answers.

Each line is `ok`, `warn`, `fail` or `skip`. A line that is not `ok` names the
fix. The exit code is non-zero only for a `fail`.

## Jobs: what chap-core ran

```text
ID           TYPE               NAME                                   STATUS   STARTED  DURATION
f293520a...  create_prediction  eval-make-prediction-ewars             SUCCESS  25m ago  15s
e3e9f243...  create_backtest    eval-chapkit-rwanda-malaria-bym-model  FAILURE  30m ago  10s
501d5b5d...  create_backtest    eval-chapkit-ghr-model                 SUCCESS  33m ago  2m 9s
```

- A failed job says why in `chaps jobs logs ID`, and nowhere else.
- `chaps jobs show`, `cancel` and `delete` take an id, or its first characters.
- `--status FAILURE`, `--type create_backtest` and `--limit N` filter the list.

## `chaps api`: one authenticated request

```sh
chaps api GET /v2/services
chaps api POST /v1/analytics/make-dataset --data @dataset.json
chaps api GET /v1/jobs/59159ad4-893b-4bbf-a855-70a38c3fb787
```

- The base URL and the `Authorization: Bearer` header of this deployment are
  filled in.
- JSON comes back pretty-printed. A JSON string prints as its text.
- Exit code **0** for a 2xx, **1** for a 4xx or 5xx, **2** when chap-core does
  not answer.

## Backup and restore

```sh
chaps backup create                       # the database, the model data, the files
chaps backup restore chaps-backup-mychap-20261004-101500.tar.gz
```

- One `tar.gz`: `manifest.yaml`, the project files, a `pg_dump` of the
  database, one tar per model and per component volume.
- `tar -tzf` reads it. An admin can restore it by hand.
- `restore` prints what it will overwrite and stop, then asks. `--yes`
  answers in advance.
- The caches (`logs`, `runs`, `renv`, `uv`) are left out.

---

## Several deployments on one machine

- Each `chaps init` directory is a deployment with its own containers, data and
  compose project name.
- They share only the host ports. Two ways:
  - **Take turns:** `chaps up` sees the other deployment on the port, and
    asks to stop it. Its data is kept. `--replace` answers in advance.
  - **Their own ports:** `--api-port 8701 --port-base 5101`, and
    `--ocs-port`, `--dhis2-port`.
- `chaps cleanup` deletes what deployments whose directory is gone left in
  docker, after it asks.

---

## Container labels and `chaps top`

Every container that chaps starts carries labels:

| Label | Value |
| --- | --- |
| `com.winterop.chaps.role` | `chap-core`, `model`, `ocs`, `s3` or `dhis2` |
| `com.winterop.chaps.model` | the marketplace id of a model |
| `com.winterop.chaps.kind` | `init` for a deployment, `run` for a `chaps run` group |

`chaps top` uses them to show every deployment on the machine as one live
tree: each service with its state, CPU, memory and URL. `l` shows a log, `s`
stops a model.

## Offline

- The marketplace comes from the network, then a cache, then a snapshot that
  is compiled into the binary.
- `--offline` never touches the network. A laptop with no connection still
  resolves the catalogue.
- `chaps update` is the one command that refuses to run offline: a plan from
  an old catalogue is not a plan.
- `chaps doctor --offline` skips the network checks, and says so.

## One model, no deployment: `chaps run`

```sh
chaps run chapkit_ewars_model
```

```text
running chapkit_ewars_model on http://localhost:5001 (answered in 41s)
```

- A marketplace id, a GitHub URL, a ghcr image or a local image.
- No directory to keep: the model runs in a group under chaps' data directory.
- `chaps ps` lists the models, and `chaps stop` stops them.

See the **chaps run** deck for groups, ports and `chaps top`.

## The chap CLI, without Python: `chaps chap`

```sh
chaps chap eval --model-name chapkit_ewars_model \
  --dataset-csv laos_subset.csv --output-file ewars.nc
chaps chap plot-backtest ewars.nc --output-file ewars.html
```

- chap-core's own `chap` CLI runs in chap-core's image.
- Your directory is mounted, so the files are on your machine.
- A model id starts that model only. No `chaps up`, no chap-core.

See the **chap CLI** deck.

## DHIS2 and the Modeling App

```sh
chaps init mychap --with dhis2 --models default
cd mychap && chaps up
chaps dhis2 connect
```

`chaps dhis2 connect` makes the `chap` route from DHIS2 to chap-core,
installs the Modeling App and the Climate App, and generates analytics.
`chaps dhis2 use URL` points it at a DHIS2 that runs elsewhere.

See the **Modeling App** deck.

## Rules chaps keeps

- **Every command reports.** It says what it found, what changed and what to
  do next. No command exits in silence.
- **Messages name the file or the command,** and give the way out on the same
  line.
- **State is checked, not assumed.** "up" means chap-core answered.
- **Nothing needs the network that does not have to.**
- **`.env` is written once.** The database password in it outlives everything
  else.
